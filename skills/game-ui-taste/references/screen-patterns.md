# Screen patterns

Choose the structure that matches the task; do not treat these as wireframe templates.

| Screen | Focal relationship | Frequent failures | Verify |
|---|---|---|---|
| Main / pause | game identity + ordered actions; background serves reading | marketing headline, equal-weight CTAs, meaningless cards | first focus, resume/back, input prompt consistency |
| Combat / exploration HUD | world and reticle first, stable peripheral state | redundant badges, giant panel coverage, low-contrast markers | busy world, damage, low health, subtitles, safe area |
| Rhythm HUD | timing lane/target first; score and streak secondary | obscured hit window, noisy animation, unstable counters | fast notes, streak loss, multiplayer lanes, latency-sensitive feedback |
| Inventory / loadout | slots or list + selected item + compare/equip | excessive wrappers, tiny icons, missing cost/context | full/empty, sort/filter, stable selection, comparison, unavailable items |
| Shop | products and real prices + purchase consequence | generic ecommerce page, unclear currency, fake discounts | affordability, confirmation, pending/failure, updated balance |
| Crafting | output and ingredients + recipe/action | recipe ambiguity, hidden shortage, misleading quantity | missing items, maximum amount, cancel and repeat |
| Dialogue | speaker, text, choices, world relationship | decoration competing with text, advancing accidentally | long localization, skip, auto advance, choice focus, subtitles |
| Character selection | character/model and meaningful choice | equal cards competing with character, redundant stats | disabled characters, selection persistence, multiplayer join |
| Results | outcome, score/reward then next action | walls of metric cards, redundant victory copy | success/fail, skip animation, confirmed reward and next step |
| Settings | current values and familiar control groups | bespoke controls with unclear semantics, too much ornament | remap, reset, apply/revert, long labels, focus |
| Mobile game | reachable actions + protected gameplay area | desktop layout merely shrunk, tiny hit areas, covered gestures | notches, touch, orientation, keyboard, multi-touch |
| Diegetic UI | physical affordance and camera/world relationship | illegibility for aesthetic, occlusion, inaccessible fallback | distance, motion, light, alternative access |

For action screens consider persistent vs contextual elements and priority conflicts (e.g. damage indicator vs dialogue). For planning screens keep comparable values visible or accessible without memorizing them. For multi-screen work establish shared navigation, focus, header/back behavior and visual language. Do not force every screen into the same panel layout: unity comes from the system, not identical composition.
